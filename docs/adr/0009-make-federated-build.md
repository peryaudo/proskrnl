# ADR 0009 — Plain Make; foreign builds stay native (federated superbuild)

**Status:** Accepted

## Context
proskrnl assembles three independently-built components: the kernel (freestanding C, clang
`--target=x86_64-elf`), Wine (autotools + winegcc/winebuild), and — at the optional final
milestone — the ReactOS shell (CMake + RosBE). The question is what builds *our* code, and
how the three are joined.

The integration boundary is **artifacts, not build graphs**: Wine and ROS are built by their
*own* build systems into PE binaries, which `tools/mkimage.sh` bakes into a FAT32 image
alongside the kernel. Nothing in our build calls into Wine's autotools or ROS's CMake at the
graph level — we invoke their native builds (`user/wine/build.sh` wraps `./configure && make`)
and collect the `.dll`/`.exe` outputs. This is the FreeBSD-ports / superbuild model, and it
mirrors the project's own "clean, observable, artifact-shaped boundary" thesis. So the choice
of *our* build system is decoupled from Wine/ROS: neither Make nor Meson integrates them;
both merely shell out.

The decision therefore rests on kernel-build fit. The kernel's build is idiosyncratic:
custom linker scripts, a Multiboot2/Limine payload, `.S` files with bespoke flags,
`objcopy`-to-flat-binary, and headers generated by `tools/gen_abi.py` / `gen_syscalls.py`
consumed before compile. Make expresses each as a one-line "command turns X into Y" rule;
Meson requires wrapping the same steps in `custom_target`s and dislikes orchestrating a
foreign `./configure && make`. Meson's real strengths (cross-files, ninja, automatic
dependency tracking, `meson test`) are strongest for ordinary hosted multi-TU projects — not
a small freestanding kernel whose hard parts are codegen, linker scripts, and artifact
assembly.

## Decision
Build the kernel and the top-level superbuild with **plain Make**. Keep every foreign
component on its **native** build system (Wine → autotools via `user/wine/build.sh`; ReactOS
shell → CMake/RosBE), joined only by PE/ELF artifacts through `tools/mkimage.sh`. Do **not**
port Wine or ROS into our build system.

## Consequences
- Kernel build states linker scripts, `.S` flags, `objcopy`, and generated-header steps
  directly, without fighting a higher-level abstraction.
- The top-level target is a thin orchestrator: build kernel → run `build.sh` → run
  `mkimage.sh`. No build system owns the whole graph, matching the federated design.
- Wine/ROS build risk (flag-combination extraction — `docs/12`, `docs/06`) lives entirely
  inside their native builds and is unchanged by our choice; we neither inherit nor mitigate
  it via the build system.
- Gives up Meson's ergonomics (ninja speed, cross-files, built-in test runner). Accepted:
  those wins are marginal for a freestanding kernel and are outweighed by Make's fit and the
  risk of a contributor trying to unify the three builds under one graph.
- The two-mode test build (oracle mingw `.exe` vs. freestanding proskrnl client) stays a
  per-target flag set in `tests/run/run.sh`, consistent with this model.
