# The GUI winetest manifest (tests/run/run.sh winetest-gui): the GUI half of
# the winetest frontier — every subtest of Wine's own user32 test module, run
# on proskrnl over the full GUI stack (win32u + wineserver-lite + winefb).
#
# WHAT IS IN THIS FILE is decided by manifest.txt's PLACEMENT RULE, not by the
# module a pair comes from: a pair that CAN pass on the CUI leg's machines
# lives there, a pair that CANNOT lives here. So this file holds every user32
# pair, and also the pairs of CUI modules whose subject needs a desktop —
# ntdll:om, ntdll:rtl, kernel32:toolhelp, ws2_32:sock, ws2_32:protocol. A GUI
# blocker places a pair here even when it has non-GUI blockers too: where it
# can eventually pass is what places it, and the rest is triage that travels
# with it.
#
# COVERAGE IS THE COMMENTS, THE GATE IS THE ACTIVE LIST, exactly as in
# manifest.txt. Active today: user32:msg — GUI-5's trophy, whole-module and
# budget-ratcheted, the block below is its whole story — and user32:wsprintf,
# measured green on both halves. Every other user32 pair is listed at the end
# of this file, parked and unmeasured, each with the TODO that says so, and so
# are the three CUI-module pairs whose subject needs a desktop.
#
# There IS an oracle half, and there was not until the oracle got a display.
# Through GUI-6 the pinned wine was built --without-x, and under its null
# display driver user32 refuses every window ("The graphics driver is
# missing"): msg.c failed its very first CreateWindow and then hung forever
# in test_SendMessage_other_thread's INFINITE wait, so the recorded oracle
# baseline was `cannot run`, not a count. The oracle is now --with-x on an
# Xvfb the runner starts (tools/setup_linux.sh, tests/run/run.sh
# start_xvfb), and run.sh winetest-gui runs THIS pair on both sides.
#
# The oracle half is not the spec authority and the switch did not make it
# one — an X11 message environment is no more "what NT does" than nulldrv
# was. The spec is still msg.c's own ok()/todo_wine assertions: winetest is
# third-party, Windows-verified spec (docs/08), and todo_wine evaluates on
# proskrnl exactly as on Wine (docs/03 "M10 winetest notes"). What the
# oracle half buys is a SECOND RUN of the same code — the same unmodified
# user32/gdi32/comctl32 above the same win32u, with only the display driver
# and what is under it different — so that the kernel half's number has
# something to be a number ABOUT.
#
# ONLY THE KERNEL HALF IS BUDGETED. The budget field below is a ceiling over
# proskrnl's divergences plus a machine-speed band; it only ever goes DOWN and
# its end state is 0. The ORACLE half is demanded green, like the CUI leg's:
# a budget is a ceiling over OUR divergences, and on unmodified Wine running
# its own suite nothing is ours. It briefly had a ceiling of one
# (msg-budget-oracle.txt, retired) for a stale todo_wine tag in msg.c that
# both Wine and proskrnl satisfy; that is fixed in the fork's suite where it
# lives. docs/03 "GUI-5 winetest notes" records the whole policy.
#
# The kernel half's ceiling used to live in a file of its own
# (msg-budget.txt). It is a property of the PAIR, not of the leg that runs it,
# so it is where every other per-pair number is — and any pair in either
# manifest can carry one.
#
# Syntax: `<exe>:<subtest>[:<budget>][:<timeout_s>]`, manifest.txt's header
# has the full grammar; both fields are positional, so the msg line spells its
# budget and its timeout (one whole msg run outlasts the 300 s default under
# TCG).
# ---------------------------------------------------------------------------

# --- user32 (third_party/wine/dlls/user32/tests) ----------------------------
# THE TROPHY, AND THE ONE BUDGETED PAIR IN EITHER MANIFEST. 16 is a CEILING,
# not the measured count, and deliberately so; only ever ratchet it DOWN, in
# the same commit as the fix that earned it (G13). The leg fails on any count
# above it, and on any CRASH exit regardless of the number.
#
# THE MACHINE UNDER IT MOVED, and the number has not been re-measured. There
# is one conhost now and it links the real user32/gdi32, so it is a desktop-
# server client at image load and connects BEFORE the test does; and the boot
# has been through the full wine.inf. Neither can produce a false green -- a
# ceiling only ever fails upward -- but if this leg goes red without a code
# change, re-measure and ratchet rather than assuming a regression, and note
# in the same commit which half of the stable list moved.
#
# Because the count's volatile part tracks machine speed (below), CI treats
# this leg as ADVISORY on pull requests and BLOCKING on main — the `msg`
# shard and the `all-green` job in .github/workflows/test.yml, reasoned out
# in docs/03 "GUI-5 winetest notes". The number is unaffected: it is still a
# ceiling, still only ever ratcheted down, and a crash exit still fails the
# leg wherever it runs.
#
# The named divergences behind the current number are listed in docs/03
# "GUI-5 winetest notes"; 0 is the end state, and build/tests/
# winetest-gui-msg.log names whichever are left after any run
# (tools/unscreen.py replays them out of the console screen diff).
#
#   23  first honest measurement (the module runs end to end)
#   20  the process idle event is a GUI-process thing
#   18  the forced desktop window no longer re-homes the process
#   17  the two speed-dependent families cannot both be at maximum
#   16  the ShowWindow(SW_SHOWMAXIMIZED) todo tags are retired in the fork's
#       suite (BOTH of them -- the sequence flag and the entry's own
#       msg_todo, the second only visible once the first was gone), so
#       passing that sequence stops costing a failure. Derived when written
#       and CONFIRMED since: the run below measures 13 and the ShowWindow
#       todo-success is absent from it on proskrnl's side too.
#
# MEASURED, this pin, on a TCG container (build/tests/winetest-gui-msg.log
# names every one): 13 = 12 "Test failed" + 1 "succeeded inside todo".
#
#   5  test_PeekMessage3 (msg.c:14708-:14779) -- the volatile timer family,
#      five of its seven on the failing side this run
#   2  the explorerless fixture: test_SetForegroundWindow (msg.c:16887) and
#      test_SetFocus (msg.c:20062)
#   5  test_WM_COPYDATA (msg.c:21285-:21315), failing as a block
#   1  msg.c:18349 succeeding inside its todo block -- the "we are faster than
#      Wine" term
#
# Two things that run says, and neither lowers the ceiling on its own. The
# INTERTHREAD pair did not fire at all: that is one run, not a fix, and the
# ratchet moves on fixes (a triage or a second confirming run is what would
# take the bound to 14). And the timer family and msg.c:18349 DID co-occur,
# which the arithmetic below used to say they could not -- the anti-
# correlation is a gradient, not a switch, so the bound now rests on the
# weaker and measured claim that the two together stay within seven.
#
# The count has two parts.
#
#   STABLE: two from the explorerless-image fixture (the desktop window
#   has no owning thread; GUI-6 retired the fixture only on explorer-
#   bearing images, and this image was kept explorerless by decision --
#   docs/03 "GUI-2 notes". They flip, -2, the day this image gains
#   explorer), five in test_WM_COPYDATA (a child process must create its
#   window inside the test's own one-second FindWindow poll, and a process
#   start on this stack costs more than that under TCG - they fail as a
#   block, so they cost no headroom), and ONE todo_wine tag that is stale
#   here because proskrnl passes what Wine fails (winetest counts a success
#   inside a todo block as a failure, so being RIGHT costs one). It was two;
#   the ShowWindow one is retired in the fork's suite, where a tag that BOTH
#   unmodified Wine and proskrnl satisfy belongs.
#
#   VOLATILE, 0..7: test_PeekMessage3 sets a 100 ms timer, never kills it,
#   and then asserts seven times that the queue is empty - true where the
#   intervening block runs in microseconds, false where 100 ms of guest
#   time passes first (Wine's own restart_timer makes a late timer due
#   immediately). Measured runs have put 1 and 4 of the seven on the
#   failing side with nothing else changed.
#
# The ceiling is what the count can reach on the SLOWEST machine that still
# runs the suite, and it is not the sum of every family's maximum, because
# two of them move in OPPOSITE directions with machine speed:
#
#   slower  test_PeekMessage3 fails more of its seven (more guest time
#           elapses per block), and test_WM_COPYDATA keeps failing all five;
#   faster  those timer assertions pass, but msg.c:18349 starts failing - it
#           is a stale todo_wine on a 500 ms wait, so it counts against us
#           exactly when we are fast enough to BEAT Wine.
#
# The measured run above has FIVE of the seven timer assertions failing and
# msg.c:18349 counting as well, so this is a trade, not an exclusion: the
# machine that fails more of the seven is the machine that stops winning the
# 500 ms race, and the two together have not exceeded seven on any machine
# measured. That sum is what the ceiling below budgets for. The bound is
#
#   2 (explorerless fixture) + 2 (interthread) + 0 (todo, ShowWindow: the
#     tags are gone) + 5 (WM_COPYDATA)
#     + 7 (test_PeekMessage3 and msg.c:18349 TOGETHER: measured at 5+1 on
#          this container, and the two trade against each other with machine
#          speed rather than adding)
#   = 16
#
# and a run above it is a real regression rather than a slower runner.
#
# The ratchet moves only when a STABLE failure is fixed: a run measuring 12
# rather than 15 has not earned a lower budget, it just got lucky with the
# timer. Ratchet from the bound, never from the measurement. The next real
# drop is the interthread pair (-2, to 14); collapsing the volatile range
# itself needs deterministic guest time (QEMU -icount), which would slow
# every leg and is not worth it for this alone.
user32_test.exe:msg:16:3000
