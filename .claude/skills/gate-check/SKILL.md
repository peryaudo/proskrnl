# gate-check

Review the working-tree diff for violations of proskrnl's hard gates. LLM contributors violate these by default, so be adversarial — assume a violation is present and try to find it.

## Steps

1. Get the diff: `git diff HEAD` (and `git diff --cached` if staged). If the user passed `$ARGUMENTS`, treat it as a path/ref to scope the review.
2. Read `docs/09-constitution.md` and `docs/CONTRIBUTING.md` for the current canonical wording — do not rely on memory of the gates.
3. Evaluate the diff against each gate below. For each, output **PASS** / **FAIL** / **N/A** with a one-line reason and `file:line` evidence.

## Gates

- **G1 — Boundary only.** Does it reproduce NT behavior *exactly* only at the observable boundary (`Nt*` semantics Wine uses; PEB/TEB/RTL_USER_PROCESS_PARAMETERS/KUSER_SHARED_DATA; NT file semantics)? Flag any Microsoft-compatible reproduction of *non-boundary* internals.
- **G2 — No NT-absent entities in core.** Anything NT lacks entering `kernel/`, `abi/`, `arch/`, `fs/`, or the `Nt*` surface? Watch for IRQL, a separate cache manager (`Cc`), DPCs, fine-grained locks, PnP/IRP, POSIX idioms. The only allowed NT-absent additions are new devices/processes at the *outside* of the boundary, and each must have a `docs/10-hacks-ledger.md` entry (see `/log-hack`).
- **G3 — Stupidly correct.** Any copy-on-write, page eviction / deferred writeback, multiple dispatcher locks, SMP/preemption assumptions, or Paged/NonPaged pool split? Each must be justified in `docs/03-nt-deviations.md` against user-observable semantics — never performance.
- **G4 — Generated contract.** Any hand-typed or model-recalled numeric constant in `abi/` (NTSTATUS, info-class numbers, struct offsets, flags)? These must come from `tools/gen_abi.py` over Wine headers, with `static_assert(offsetof(...) == ...)`. Flag magic numbers.
- **G5 — Test first.** Does new boundary behavior have a `tests/ntapi/` test that is green on Wine/Windows *preceding* the kernel code? Flag kernel behavior added without a prior test.
- **G6 — Conviction by differential test.** Is any fix justified only by "sanitizer/assert went quiet" rather than a passing differential/conformance test?
- **G7 — Additive & removable.** Is any out-of-core feature (GUI, WOW64, ROS shell) wired in such that deleting its directories would not restore the core intact?
- **G8 — Constants cite a trusted source.** Does the diff introduce a hand-typed numeric constant whose value is fixed by an external contract (hardware register numbers/bit positions, MSRs, on-disk format fields, NT magic addresses/limits) without a comment in the same file naming a trusted source to re-verify it against (pinned Wine tree path + symbol, official MS docs, vendor spec — Intel SDM / datasheet / virtio — or the pinned QEMU tree)? Where feasible, actually re-verify the value against the cited source (grep `third_party/wine` / `third_party/qemu`) rather than trusting the comment. Purely internal choices (pool bases, KASAN shadow, our own syscall numbers) are exempt — but check they are not silently load-bearing for an external contract.
- **G9 — Wine patched only at the unixlib seam.** Does the diff bump the `third_party/wine` submodule pin or touch Wine build glue? If so: inspect the submodule diff vs. the winehq base (`tools/hack_meter.sh`; the base is the fork's `master` branch, which a base bump fast-forwards in the same push that rebases `proskrnl-target`) — does any change alter PE-side observable behaviour rather than unixlib plumbing or build glue? **Dormancy (docs/06 "One tree, three roles"):** does any fork-commit hunk touch shared PE code *outside* a `!__wine_unix_call_dispatcher` guard? Does any change mutate a `server/` (or other) file that enters a binary the oracle executes, rather than adding a new file/build target? Does each commit header state its dormancy mechanism? Does any change exist to make a failing proskrnl differential test pass — i.e. does it edit the oracle instead of the kernel (cross-check Art. 6)? Is any Wine modification carried outside the fork (a patches directory, vendored diffs, build-time patching)? All Wine changes must be commits on the fork's `proskrnl-target` branch, each carrying the required header (what it changes / why the seam is the right place / upstream disposition: `upstreamable`, `proskrnl-only`, `temporary`-until-named-feature). Does the PR description report the old → new hack-meter line counts with a justification for any growth, and state that `tests/run/run.sh oracle` was re-run green against the new pin (the dormancy proof)? For a new seam, compare its shape against the canonical worked example — the fork's conhost seam commit ("conhost: pump the kernel ConDrv transport when no wineserver is below"; docs/06 "Landing a fork commit"): a side-effect-free probe first, the proskrnl leg guarded behind behaviour only a missing unixlib produces, the implementation in new files dead under the oracle. A seam that invents a different arrangement without stating why the conhost shape cannot serve it deserves scrutiny.
- **G10 — No parallel engines.** Does the diff resolve object names, perform create/open access checks, allocate handles, or mint identity values (ids, cookies) through code that is not the existing Ob/Ps engine? Look for private lookup/walk/allocate loops in departments other than the engine's own — the `a53dd04` shape: Cm's private name-resolution path skipped the zero-access refusal Ob's open engine already enforced, and only the fuzzer caught the drift. A specialized parallel path FAILS **even if its behaviour currently matches the engine's**; the fix is to route through the engine (extending it with a parse hook or flag where needed), or an explicit justification in the PR of why the engine cannot serve the case.
- **G11 — Ownership audit.** If the diff creates, copies, or stores an identity value (thread/process ids, cookies, handle values), or touches object creation, reference counting, or teardown, run the audit and report the answers explicitly — never skip the bookkeeping:
  1. **Identity:** list every identity value the diff writes. For each, name the single authoritative source, then check whether a second assignment site now exists anywhere (grep for other writers). The `4fc732c` shape: the TEB got id N while the ETHREAD counted N+1, because two sites each minted "the" thread id.
  2. **Lifetime:** list every object whose creation/refcount/teardown the diff touches. For each, name who holds a reference at every point of its life, then walk the two hostile schedules: (a) every handle is closed at the earliest legal moment; (b) the owning thread exits before its creator/waiters act. The `edf9f0b` shape: ntdll's threadpool closes its worker-thread handles immediately, and the live thread's ETHREAD was deleted out from under it. "The caller won't do that" is a FAIL; the required answer is a reference the running code itself cannot drop.
- **G12 — Loud refusal.** Does the diff introduce a stub, default case, or stand-in that fabricates a plausible answer instead of refusing loudly? Hunt for the shapes that shipped as bugs: a no-op body returning `STATUS_SUCCESS` (`1d6dafd`: silent `NtResumeThread`); a query answering a hardwired or caller-independent value — a fixed exit status, count, id, or device type (`7cd6189`: `STILL_ACTIVE` forever; `87bb03e`: hardwired `STATUS_PENDING`; `3ce0031`: every device `FILE_DEVICE_DISK`); an accept-and-do-nothing implementation of a synchronization primitive (`4fc732c`: alert-by-tid fakes → busy spin); a glue stand-in returning a sentinel the caller interprets (`15e72d8`: `VkKeyScanW` −1 → literal `^M`). Concretely: for every new `switch` default, early return, and TODO-adjacent body in the diff, ask "could a caller distinguish this from the real implementation except by failing later?" If not, it must instead return `STATUS_NOT_IMPLEMENTED` AND name itself on serial (the `KI_SYSCALL_MISSING` pattern). PASS a fixed answer only if the diff shows its oracle provenance — a `tests/ntapi/` pin green on the oracle or a `docs/03-nt-deviations.md` entry (e.g. `NtQueryTimerResolution`'s fixed triple is Wine's own behaviour); an uncited fixed answer FAILS even if it happens to match, for the same reason as an uncited constant (G8). **`STATUS_NOT_IMPLEMENTED` is never a fixed answer with provenance** — it means *unbuilt*, and an oracle that answers it is unbuilt too, never authoritative. So FAIL: any `tests/ntapi/` case asserting `STATUS_NOT_IMPLEMENTED` (grep the diff's test files for it — a refused case is skipped with a comment, never pinned); and any mechanism that exempts a refusal from the dispatcher's panic (the removed `KiPinnedNotImplemented` shape — a latch, flag, or wrapper marking a refusal "intended"). Every `STATUS_NOT_IMPLEMENTED` a ring-3 syscall answers must reach `kernel/syscall/table.c`'s panic. A refusal a real caller depends on is a different status entirely — the specific NT failure for the case (`STATUS_INVALID_INFO_CLASS`, `STATUS_INVALID_DEVICE_REQUEST`, …) — implemented and pinned like any other behaviour.
- **G13 — Commits are meaningful units.** This gate reviews the branch's commit structure, not the flattened diff: run `git log --format='%h %s' origin/main..HEAD` (skip if reviewing uncommitted work only — then note G13 as pending until commits exist) and inspect each commit's own diff (`git show --stat <h>`). FAIL on: a commit mixing unrelated concerns (a behaviour change bundled with a drive-by refactor/rename/format sweep); a vague or department-less subject ("fix stuff", "WIP", "checkpoint", bare "updates"); a nontrivial commit whose body does not state what/why and how it was verified; a kernel-behaviour commit whose G5 oracle pin lands in the same commit or after it (the pin must precede — that ordering is the only proof the test was green before the implementation existed); fixup/squash noise surviving into the PR. Where a commit looks non-self-contained (a later commit fixing an earlier one's build), flag it for local squash/reorder before push. The standard is the repo's own history: `ke+ps: three boundary fixes the full-suite proskrnl run flushed out` with a per-fix body is the bar.

- **G14 — The blocking frontier is declared.** Run `python3 tools/blocking_frontier.py --check` — it is cheap and mechanical, so actually run it rather than eyeballing. FAIL on any check failure. If the diff widens the frontier (a service newly able to park, i.e. a new `tools/blocking_frontier.txt` row): the baseline regeneration must be in the same commit as the widening, and that commit's body must state the widening and its reason; also check the diff (or its docs) re-answers `docs/20`'s §8.4 question for the new blocking point — the STILL-TRUE tables were written against the old frontier. A baseline row with no acknowledging sentence FAILS even when the widening is correct. If the diff adds a non-blocking region (a `KiEnterNoBlockRegion` bracket), check the same region is in the tool's `MUST_NOT_BLOCK` list — the static and runtime halves must name the same set.

## Provenance (also fail-worthy — see docs/11-licensing.md)

- GPL-source translation into kernel/drivers (drivers must come from public specs).
- Kernel reference material other than Wine headers + official MS docs (no ReactOS/leaked source/model memory).
- Missing `docs/provenance.md` entry for a new borrowed component.

## Output

End with a verdict: **READY** (all applicable gates pass) or **BLOCKED** (list the failing gates). Be concrete and cite lines; do not soften a real violation.
